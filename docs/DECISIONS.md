## [2026-08-27] pgx (нативный) вместо database/sql+lib/pq для storage
Контекст: в схеме БД есть price_usd NUMERIC — тип, требующий точной работы
с decimal без потерь точности. storage — единственный модуль, работающий
с БД напрямую, специфичные типы драйвера наружу не протекают.
Решение: используем pgxpool.Pool (jackc/pgx/v5) напрямую, без
прослойки database/sql. Ключевая причина — встроенная поддержка decimal-типов
через pgtype.Numeric без ручного Scan/Value и сторонних библиотек.
Дополнительно: lib/pq не развивается, pgx — текущий стандарт для Go+Postgres.
Альтернативы:
database/sql + lib/pq — отклонено: NUMERIC требует ручной обвязки
(строки или shopspring/decimal вручную), библиотека не развивается.
database/sql + pgx как драйвер (через stdlib) — отклонено: теряется
часть нативных преимуществ pgx (типы pgtype) ради портируемости, которая
здесь не нужна, т.к. storage и так изолирован.
Риски: тестирование репозиториев через моки — pgxmock менее зрелый
и менее документированный, чем sqlmock. Учесть при написании тестов
на QA-этапе.

## [2026-08-28] Binance public API вместо CoinGecko для источника курсов
Контекст: collector опрашивает BTC/ETH раз в 5 мин (~24 запроса/час) — объём
тривиальный для лимитов любого провайдера, поэтому выбор идёт не по квотам,
а по простоте интеграции и числу движущихся частей.
Решение: используем Binance public REST API (`GET /api/v3/ticker/price`,
без ключа и регистрации) как источник текущей цены BTC/ETH в USD.
Альтернативы: CoinGecko (агрегированная цена по биржам) — отклонено на
старте: анонимный доступ нестабилен по лимитам, для стабильности нужен
Demo-ключ, то есть доп. внешняя зависимость (аккаунт + секрет в конфиге),
не оправданная при таком объёме запросов. Можно рассмотреть как апгрейд
после защиты, если понадобится именно рыночный агрегат, а не цена одной
биржи.

## [2026-08-28] Планировщики: фиксированный тикер в collector, DB-driven поллинг в bot
Контекст: два шедулера разной природы — collector работает с фиксированным
интервалом от старта процесса, bot рассылает по индивидуальному
interval_minutes на пользователя.
Решение:
- collector: `time.Ticker(5 * time.Minute)` в горутине монолита, без
  внешних библиотек.
- bot: общий `time.Ticker(1 * time.Minute)`; на каждый тик — запрос к
  subscriptions на предмет "созревших" (last_sent_at + interval_minutes
  <= now()), рассылка, обновление last_sent_at.
Альтернативы: cron-библиотека (robfig/cron) — отклонено, привязки к
календарным моментам нет, только "каждые N минут", библиотека избыточна.
Отдельный in-memory таймер на подписку — отклонено: состояние теряется
при рестарте контейнера, требует пересборки таймеров из БД при старте без
явного преимущества перед поллингом.
Риски: гранулярность в 1 минуту — интервалы короче минуты не поддержаны
ни схемой (interval_minutes), ни тикером; сейчас это не требуется.

## [2026-08-28] Отдельная колонка last_sent_at вместо переиспользования updated_at
Контекст: шедулеру bot нужно "когда последний раз отправили", а updated_at
в текущей схеме subscriptions обновляется при любом изменении подписки
(например, смене interval_minutes через /start-auto) — это ломает расчёт
следующей отправки.
Решение: добавить `last_sent_at TIMESTAMPTZ` (NULL — ещё не отправляли);
updated_at остаётся только для факта редактирования записи, шедулер
трогает исключительно last_sent_at.

## [2026-08-30] net/http.ServeMux вместо стороннего роутера для api
Контекст: два простых GET-эндпойнта, Go 1.22+ уже поддерживает метод-роутинг
и path-параметры ({currency}) в стандартном ServeMux.
Решение: используем http.ServeMux без внешних зависимостей.
Альтернативы: chi/gorilla/mux отклонены как избыточные для текущего
набора маршрутов; можно пересмотреть, если появятся middleware-цепочки,
группировка роутов или более сложный матчинг.

## [2026-09-03] internal/domain как единый слой сущностей
Контекст: ревью показало, что "монета/курс" была размазана по трём разным
представлениям — storage.Rate (с pgtype.Numeric), api DTO (с JSON-тегами)
и голые string/float64 в collector общей доменной модели не было.
Решение: завели internal/domain с Currency (валидируемый string-тип через
NewCurrency) и Rate/RateStats. storage конвертирует pgtype.Numeric ↔ domain
на границе с БД, api конвертирует domain ↔ JSON-DTO на границе с HTTP.
Зависимость односторонняя: storage/api/collector зависят от domain, domain
ни от кого не зависит.
Альтернативы: закрытый enum валют (только BTC/ETH) отклонено в пользу
открытого типа с regex-валидацией (`^[A-Z]{2,10}$`), чтобы добавление новой
отслеживаемой валюты не требовало правки domain-пакета.
Риски: Go не может запретить обход конструктора NewCurrency для defined-типа
на основе string (domain.Currency("xxx") скомпилируется) валидация это
конвенция на границах системы, а не гарантия компилятора.

## [2026-09-03] Разделение internal/binance и internal/collector
Контекст: ревью отметило, что источник цен (Binance) и бизнес-логика сбора
(цикл опроса, запись в storage) были физически в одном пакете collector,
хотя и так были не завязаны друг на друга напрямую по коду.
Решение: вынесли клиент Binance в отдельный internal/binance. collector
знает только про интерфейс PriceFetcher (объявлен в самом collector),
реализацию передают снаружи через New(...) в main. Замена источника цен
(например, на CoinGecko) не потребует правок в collector.

## [2026-09-03] slog вместо стандартного log
Контекст: ревью отметило отсутствие структурированного логирования.
Решение: переход на log/slog (стандартная библиотека, без внешних
зависимостей) с JSON-выводом (slog.NewJSONHandler). Логгер создаётся один
раз в main и передаётся в collector/api через конструктор (New(...,
logger)), а не создаётся внутри каждого пакета — единый формат логов
на всё приложение.

## [2026-09-03] Dockerfile + сервис app в docker-compose
Контекст: ревью отметило, что docker-compose поднимал только БД, само
приложение запускалось только локально через go run — не было единого
способа поднять весь стек.
Решение: добавлен multi-stage Dockerfile (сборка в golang:1.25-alpine,
финальный образ на alpine:3.20 с одним бинарём, CGO_ENABLED=0 для
статической линковки). В docker-compose.yml добавлен сервис app с
зависимостью от postgres через healthcheck (condition: service_healthy),
чтобы приложение не пыталось подключиться к ещё не готовой БД.
Внутри Docker-сети app обращается к БД по имени сервиса postgres,
не localhost.

## [2026-09-03] cmd/server/main.go — единая точка входа
Контекст: ревью отметило отсутствие main.go конструкторы модулей
существовали, но нигде не вызывались вместе, приложение не запускалось
как сервис.
Решение: main.go собирает конфиг (переменные окружения с дефолтами),
создаёт slog.Logger, прогоняет миграции, создаёт storage/collector/api
и запускает collector.Run и http.Server каждый в своей горутине.
Завершение — через context.Context, отменяемый по SIGINT/SIGTERM
(signal.NotifyContext), с graceful shutdown HTTP-сервера (server.Shutdown
с таймаутом 10с) вместо мгновенного обрыва соединений.
