# Журнал решений (ADR)

## [2026-08-26] Модульный монолит вместо микросервисов на старте
Контекст: срок 2-3 недели, разработка в одиночку через текстовые сессии с
Claude без агентов.
Решение: начинаем с модульного монолита с чёткими internal-границами,
выделяем сервисы только когда граница доказала свою пользу на практике.
Альтернативы: сразу микросервисы — отклонено, риск не успеть с MVP.

Контекст: нет бюджета на проект.
Решение: слой `aigateway` работает поверх локальной модели через Ollama.
Альтернативы: Anthropic/OpenAI API — отклонено из-за отсутствия бюджета,

## [2026-08-26] Выносим в отдельный сервис только aigateway
Контекст: нужно продемонстрировать микросервисный подход, но времени мало.
Решение: единственное осознанное выделение в срок — aigateway, из-за
другого профиля нагрузки (инференс модели).
Альтернативы: дробить всё сразу — отклонено как избыточное дробление
без времени на его обоснование.

## [2026-08-26] Дисклеймер во всех ИИ-ответах о трендах/прогнозах
Контекст: сервис не должен выглядеть как источник финансовых советов.
Решение: любой ответ aigateway, касающийся прогнозов/трендов, обязан
явно указывать, что это не финансовая рекомендация, и опираться на
реальные данные из БД (RAG), а не додумывать цифры.

## [2026-08-27] pgx (нативный) вместо database/sql+lib/pq для storage
Контекст: в схеме БД есть price_usd NUMERIC — тип, требующий точной работы
с decimal без потерь точности. storage — единственный модуль, работающий
с БД напрямую, специфичные типы драйвера наружу не протекают.
Решение: используем pgxpool.Pool (jackc/pgx/v5) напрямую, без
прослойки database/sql. Ключевая причина — встроенная поддержка decimal-типов
через pgtype.Numeric без ручного Scan/Value и сторонних библиотек.
Дополнительно: lib/pq не развивается, pgx — текущий стандарт для Go+Postgres.
Альтернативы:
database/sql + lib/pq — отклонено: NUMERIC требует ручной обвязки
(строки или shopspring/decimal вручную), библиотека не развивается.
database/sql + pgx как драйвер (через stdlib) — отклонено: теряется
часть нативных преимуществ pgx (типы pgtype) ради портируемости, которая
здесь не нужна, т.к. storage и так изолирован.
Риски: тестирование репозиториев через моки — pgxmock менее зрелый
и менее документированный, чем sqlmock. Учесть при написании тестов
на QA-этапе.

## [2026-08-28] Binance public API вместо CoinGecko для источника курсов
Контекст: collector опрашивает BTC/ETH раз в 5 мин (~24 запроса/час) — объём
тривиальный для лимитов любого провайдера, поэтому выбор идёт не по квотам,
а по простоте интеграции и числу движущихся частей.
Решение: используем Binance public REST API (`GET /api/v3/ticker/price`,
без ключа и регистрации) как источник текущей цены BTC/ETH в USD.
Альтернативы: CoinGecko (агрегированная цена по биржам) — отклонено на
старте: анонимный доступ нестабилен по лимитам, для стабильности нужен
Demo-ключ, то есть доп. внешняя зависимость (аккаунт + секрет в конфиге),
не оправданная при таком объёме запросов. Можно рассмотреть как апгрейд
после защиты, если понадобится именно рыночный агрегат, а не цена одной
биржи.

## [2026-08-28] Планировщики: фиксированный тикер в collector, DB-driven поллинг в bot
Контекст: два шедулера разной природы — collector работает с фиксированным
интервалом от старта процесса, bot рассылает по индивидуальному
interval_minutes на пользователя.
Решение:
- collector: `time.Ticker(5 * time.Minute)` в горутине монолита, без
  внешних библиотек.
- bot: общий `time.Ticker(1 * time.Minute)`; на каждый тик — запрос к
  subscriptions на предмет "созревших" (last_sent_at + interval_minutes
  <= now()), рассылка, обновление last_sent_at.
Альтернативы: cron-библиотека (robfig/cron) — отклонено, привязки к
календарным моментам нет, только "каждые N минут", библиотека избыточна.
Отдельный in-memory таймер на подписку — отклонено: состояние теряется
при рестарте контейнера, требует пересборки таймеров из БД при старте без
явного преимущества перед поллингом.
Риски: гранулярность в 1 минуту — интервалы короче минуты не поддержаны
ни схемой (interval_minutes), ни тикером; сейчас это не требуется.

## [2026-08-28] Отдельная колонка last_sent_at вместо переиспользования updated_at
Контекст: шедулеру bot нужно "когда последний раз отправили", а updated_at
в текущей схеме subscriptions обновляется при любом изменении подписки
(например, смене interval_minutes через /start-auto) — это ломает расчёт
следующей отправки.
Решение: добавить `last_sent_at TIMESTAMPTZ` (NULL — ещё не отправляли);
updated_at остаётся только для факта редактирования записи, шедулер
трогает исключительно last_sent_at.
