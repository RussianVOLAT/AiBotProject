# Протокол работы над проектом (crypto-rates service)

## 0. Принцип
Claude не помнит ничего между чатами. Источник истины — этот репозиторий,
а не переписка. Любая договорённость, которая не попала в docs/, для проекта
не существует.

## 1. Структура docs/ в репозитории
- `docs/ARCHITECTURE.md` — текущая архитектура: сервисы, их границы, как общаются.
  Обновляется редко, только при реальных изменениях структуры.
- `docs/DECISIONS.md` — ADR-лог. Формат одной записи:
  ```
  ## [2026-08-25] Название решения
  Контекст: почему вообще встал вопрос
  Решение: что выбрали
  Альтернативы: что отклонили и почему
  ```
- `docs/PROGRESS.md` — живой чек-лист. Секции: "Готово", "В работе", "Следующее".
  Обновляется в конце КАЖДОЙ сессии.
- `docs/API_SPEC.yaml` — OpenAPI спека, растёт вместе с кодом.

## 2. Роли трёх аккаунтов
Модель на free-плане одна и та же на всех трёх (Sonnet 5), поэтому разделение —
не по "мощности", а по зоне ответственности. Это позволяет держать
Custom Instructions каждого Project короткими и не тратить контекст на лишнее.

### Аккаунт A — Архитектор / Планировщик
Project custom instructions (пример):
```
Ты — архитектурный консультант pet-проекта на Go: сервис курсов криптовалют
+ REST API + Telegram-бот, с AI-фичами. Стек: Go, PostgreSQL, Docker,
GitHub Actions, микросервисы (см. приложенный ARCHITECTURE.md).
Твоя роль: обсуждать дизайн, находить проблемы в решениях, вести ADR-лог.
Не пиши много кода — фокус на решениях и их обосновании.
```
Knowledge base: ARCHITECTURE.md, DECISIONS.md.

### Аккаунт B — Разработчик
```
Ты помогаешь писать Go-код для сервиса курсов криптовалют по уже принятой
архитектуре (см. приложенный ARCHITECTURE.md и текущий PROGRESS.md).
Работаем по одному модулю/сервису за сессию. Пиши идиоматичный Go,
с обработкой ошибок и минимальными комментариями по делу.
```
Knowledge base: ARCHITECTURE.md, PROGRESS.md, актуальные .go файлы модуля.

### Аккаунт C — QA / DevOps / Документация
```
Ты помогаешь с тестами (unit/integration), Docker/docker-compose,
GitHub Actions CI/CD и OpenAPI-документацией для сервиса курсов
криптовалют. См. приложенный ARCHITECTURE.md.
```
Knowledge base: ARCHITECTURE.md, API_SPEC.yaml.

## 3. Ритуал начала сессии (5 минут)
1. Открой нужный Project (не голый чат — теряешь базу знаний).
2. Если знание base давно не обновлялась — замени файлы на актуальные из репо.
3. В первом сообщении сессии кратко скажи, что делаем сегодня, и вставь
   релевантный фрагмент PROGRESS.md ("В работе"/"Следующее"), а не весь файл.

## 4. Ритуал конца сессии (2 минуты)
Попроси в конце: "Сформулируй итог сессии для PROGRESS.md: 5-8 строк,
что сделано, что решено, что дальше". Вставь результат в docs/PROGRESS.md
и закоммить.

## 5. Экономия лимита (5-часовое окно на free-плане)
- Extended thinking включай только для Аккаунта A (архитектурные споры,
  трейд-оффы). Для B и C — выключай, там нужна скорость, не рассуждение.
- Не открывай новый чат в Project ради одной короткой правки — дописывай
  в текущий, пока он не станет неудобно длинным.
- Крупные задачи дроби заранее (в PROGRESS.md), чтобы одна сессия = одна
  законченная единица работы, а не расплывчатое "доделаем как получится".

## 6. Синхронизация между аккаунтами
Раз в 1-2 сессии — беглый проход по DECISIONS.md и PROGRESS.md перед стартом
работы в другом аккаунте, чтобы Разработчик не спорил с решениями,
которые Архитектор уже закрыл.
